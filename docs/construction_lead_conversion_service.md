# CON-C012: lead conversion service

Authority: rev.12 section 5.1 and section 22; clarifications.txt CON-C012; new clarification.txt required Stage 1 HTTP boundary and one business operation -> one audit event. CON-C012 belongs to Stage 1A but its conversion endpoint is a dependency explicitly required for Stage 1 closure.

The caller must open one transaction and roll back every failure. The service locks the tenant-scoped non-deleted lead, selected client and selected project, using the existing repositories and a no-autoflush scope. It validates fresh Platform membership and grants through the shared permission engine: projects.edit for conversion of the unbound tenant lead, projects.create for new resources, projects.read for selected targets. No new permission codes, automatic grants or duplicate membership sources are added.

The command supports the three approved selections. New client requires an explicitly supplied normal person/company client_type; new project requires an explicitly supplied normal project name. Available lead address is reused, or a required missing project address can be supplied. Lead name/phone/email populate a new client. Lead responsible_user_id is checked against Platform membership for a new project. Work description and comment are retained in project.comment separated by a blank line, since the current project contract has no separate work-type field. Existing selected resources are not overwritten or reassigned.

Normal client/project creation services are reused with manage_transaction=False. Their create-audit calls are collected by a private per-attempt adapter, validated for actor/tenant/entity/trace and exact create-event payload, and represented by created resource IDs in the one persisted construction_lead_converted event. The adapter is not a global suppression option. Missing or duplicate child audit calls fail conversion. Standalone client/project operations keep their existing audit and transaction behavior. The final conversion audit includes status and link changes, never contact values or work/comment text.

Fresh conversion checks expected_row_version before resource creation. All seven non-terminal states are eligible. lost is not reopened automatically. A won repeat returns the recorded client/project with fresh authorization and validated ownership, without writes/audit/version increment; it cannot silently select different recorded targets. A failed conditional conversion write is an operation failure, not an assumed ROW_VERSION_CONFLICT: after locked validation an unexpected missing RETURNING row must not lead to success or commit. Ordinary stale locked version uses the existing ROW_VERSION_CONFLICT contract.

The conditional repository write and returned entity are checked for tenant, IDs, status, version, timestamp and preserved lead input. ConstructionLeadConversionResult is internal, not an HTTP response. Idempotency reservation/completion, commit/rollback, encrypted replay response and HTTP mapping remain the next workflow/HTTP steps.

Local tests cover all three selections and seven eligible statuses, exact single aggregate audit, replay, validation, permissions, unavailable tenant resources, ownership, failures and caller transaction ownership. SQLite integration uses the real client/project/lead repositories to verify atomic commit and rollback, including failure after a real final audit insert. A test-only UTC adapter compensates for SQLite dropping timezone metadata; production PostgreSQL has no such adapter. SQLite does not prove PostgreSQL concurrency, RLS or deployed API behavior.

This installer adds service/tests/document and the conversion event to the existing Stage 1A audit registry. No Supabase, Storage or real email operations; physical lead schema is not created. Stage 1 is not declared complete. Next: CON_C012_LEAD_CONVERT_WORKFLOW.
