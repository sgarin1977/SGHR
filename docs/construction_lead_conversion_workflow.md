# CON-C012: transactional conversion workflow

Authority: rev.12 section 5.1 and section 22; clarifications.txt CON-C012 and the mandatory convert-lead Idempotency-Key list; new clarification.txt explicitly includes the conversion endpoint in the Stage 1 API boundary and requires one audit per business operation. The new area-duplicate clarification is a separate Stage 1 dependency and does not alter conversion.

ConstructionLeadConversionWorkflow reuses the confirmed conversion service and existing shared ApiIdempotencyService/Fernet response codec. All repositories, the domain service and the ledger use one session. The caller opens the transaction; the workflow owns one final commit or rollback on failure. Reservation, new client/project if needed, conditional lead conversion, the service's single aggregate audit and encrypted idempotency completion are atomic. Standalone client/project behavior remains unchanged.

The key is mandatory. Operation construction.lead.convert is bound to tenant, authenticated user principal, key hash and raw command hash, including lead path ID, expected version and supplied target/creation fields before normalization. A processing reservation returns idempotency_in_progress (409); a reused key with a changed raw command uses the existing ApiIdempotencyKeyReusedError contract. No separate idempotency table, record ownership model or plaintext response storage is added.

The internal serializable conversion result contains only lead_id, tenant_id, client_id, project_id, won status and positive BIGINT row_version. It exposes neither token/key, ledger binding/ciphertext nor unrelated entity attributes. The encrypted snapshot adds the explicit tenant/user/operation/key/request binding. This step introduces no HTTP route or envelope; HTTP serialization/error mapping is the next step.

A completed replay must pass current Platform membership and shared permission checks, then lock a non-deleted tenant lead and verify its won state and stored links before invoking the domain service. This prevents replay from entering the fresh mutation branch. The service locks/validates the current client and project, project ownership and fresh grants. Unavailable resources or changed relationships deny replay. The original snapshot is returned after later version changes; the current lead version cannot be lower than the snapshot. Replay creates no new domain records, version increment or audit. A new key for an already converted lead can complete a new ledger record while the service remains a domain no-op.

The workflow validates reservation identity, binding and expiration, and validates completed record identity/state/status and the decrypted snapshot before committing. Errors from reservation, domain mutation, projection, audit, completion, decryption or commit cause rollback. Expected permission/scope, validation, status, not-found, row-version and key-reuse errors retain their typed contracts; unexpected failures are sanitized.

Local tests cover the three scenarios, original snapshot replay, changed raw body/path/key behavior, processing conflicts, permission loss before/after reserve, current resource/ownership checks, malformed/swapped ledger data, wiring and completion failures. SQLite integration uses the real conversion service and domain repositories, an encrypted codec and a local SQL ledger to verify atomic commit and rollback. PostgreSQL locking/RLS/concurrent requests and deployed HTTP acceptance remain unproven by these local tests.

Installer: adds workflow, tests and this document; no existing application source is modified. No Supabase, Storage or real email operations. Physical lead schema is not created. Stage 1 remains open. Next: CON_C012_LEAD_CONVERT_HTTP.
